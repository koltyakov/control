# Remote browser and human takeover

For web automation discover opt-in `browser.run`, configured with an absolute `browser.cli` executable from https://github.com/vercel-labs/agent-browser. Use `control_browser` with `request: {session:"work",args:["snapshot","-i"]}`, or `control browser run NAME --session work -- snapshot -i`. First run `--version` and `skills get core`, then read the installed guidance. Installation of agent-browser or Chrome needs approval. Default home/runtime/namespace are profile- and owner-private. Use the same session and fresh refs. Commands share `maxTasks` and serialize per owner; explicit upstream flags can override defaults, and this is not a sandbox.

For manual login or 2FA, explicitly start `control browser run NAME -- dashboard start --port 4848`, then `control browser view NAME --port 4848` to get a local loopback URL. MCP `control_browser_view` returns the URL and forward ID on the MCP server host; stop it with `control_forward_stop`. Choose a distinct worker port for each concurrently running owner dashboard. A view forwards an already started dashboard, does not verify readiness, and controls all sessions in its namespace, not just one tab. It does not expose the worker's entire desktop. Pause AI mutations during human takeover and take fresh snapshots before resuming. Passkeys/security keys are not forwarded.

CLI args/stdin remain task-visible and do not resolve Control secret references. Text results mask configured worker secrets, but live frames, files and upstream dashboard activity are not redacted. Never request passwords or verification codes in chat or retrieve secrets through a shell. Do not record sensitive streams. Closing the view only closes its forward. Explicitly run `close` in sessions you created and `dashboard stop` when finished; upstream daemons can survive Control calls/restarts and are not task lifetimes. Never replay uncertain effects. See [browser setup and workflow](https://github.com/koltyakov/control/blob/main/docs/browser.md).
