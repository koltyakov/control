# Web console

[README](../README.md) · [Gateway deployment](gateway.md) · [Users](users.md) · [Dashboard](dashboard.md) · [Protocol](protocol.md)

The gateway serves a password-protected management console at its public URL. `/` redirects to `/console`, which redirects signed-out visitors to `/login`. HTML, CSS, JavaScript, and icons are embedded in the Control binary. No frontend build, external CDN, separate web service, or Node.js runtime is needed to deploy it.

`make build` and `make bundle` strip JavaScript comments, including JSDoc typing declarations, before embedding the console. The Go bundle builder uses esbuild's Go API and a temporary Go build overlay, leaving editable sources untouched. It removes comments and excess whitespace without bundling modules or mangling names. No generated asset is checked in, and no minifier runs in the deployed binary. A direct `go build ./cmd/control` remains a development build that embeds the original source. See [D117](decisions.md#d117-strip-console-comments-during-go-bundling).

## Provision browser access

Browser passwords are separate from CLI account keys. Existing accounts have no browser access until a password is provisioned. There is no default password, public signup, or unauthenticated password-reset route.

With a saved gateway superuser login:

```sh
control console password
```

The command prints the browser username it is setting, then asks you to enter and confirm a password at hidden prompts. The operator's browser username is `@operator`. It is separate from fleet account names and remains usable only while the gateway has superuser administration configured.

To give an existing fleet account browser access:

```sh
control console password alice
```

Only the operator can select another account. An account owner can run `control console password` with their own saved account login to set or reset their own browser password. Common keys and installation credentials cannot provision passwords.

For noninteractive provisioning, use `--password-stdin`. It removes one trailing line ending and requires 12..1024 password bytes. Passwords are not accepted as command-line arguments. Do not put them in shell history or commit them to project files.

Open the gateway's HTTPS URL and sign in with the fleet account's exact, case-sensitive name or `@operator`. The sign-in page's How to get a password section shows the provisioning command. Users can change their own password on the Account page by entering their current password. Operators can set fleet passwords on the Accounts page. Every password change invalidates that login's existing browser sessions without rotating CLI keys or cancelling accepted work.

## Pages and actions

- Overview shows gateway resources with version and uptime, online and offline machine counts, and reported active work. Each count links to the corresponding Machines filter. Its table shows all online, enabled machines without a row limit, independently of the Machines search. A Hybrid host stays visible if either context is online and enabled. Offline and disabled machines remain accessible through All machines; summary counts still include the full fleet. A gateway sample older than one minute is labeled with its age.
- Machines supports name, platform, and label search, state filters (All, Online, Busy, Idle, Offline, Disabled, with counts; reserved machines count as busy), and sorting by name, state, connections, CPU, memory, or disk. The disk column shows the first sampled node path with a known size; the detail drawer lists every sampled path. Unknown values sort last in either direction. The state column also shows active work by kind, lease expiry, last activity, missing health reports, and when offline machines were last seen. The connections column shows three fixed counters: direct peers, relayed peers (TURN or gateway relay), and active tunnels; hovering one shows its breakdown. CPU shows the logical core count. A System or User tag shows whether the node runs as a boot-time service account (root, or LocalService/SYSTEM on Windows) or in a user session. Narrow screens show each machine's state and resource usage in stacked rows. Select a machine row to open its detail drawer with resources, activity, platform, version, labels, identity, rename, enable/disable, and unregister with a typed name confirmation. An offline machine shows Wake when an online machine on its verified LAN can send a Wake-on-LAN packet for it; see [console wake](wake.md#wake-from-the-console). Offline and unknown metrics are not displayed as zero. Rename changes the gateway alias, not project-local scenario files on CLI hosts.
- Add machine chooses the platform and User, System, or Hybrid startup context, then displays a one-time installation command. The target detects its architecture. Blank names or `auto` use the target's hostname. The gateway needs a published bundle with both supported architectures for that OS. The dialog watches invitation redemption and then requests a fresh status snapshot before reporting the redeemed identity online. Hybrid completion requires both identities online in their expected contexts. **Connection → Through worker** appears only when a selectable proxy exists. It selects a ready endpoint, with legacy managed standby compatibility. The target must reach the selected address. The dialog verifies the gateway echoed the selection and shows it with the command and in Invitations.
- Every machine menu offers **Gateway proxy**, whether hosting is enabled or not. Disabled hosting has no drawer section. Configured hosting shows readiness and enrolled machine counts, grouping a Hybrid User/System pair once and omitting zero counts. Inspection lists native live private interface addresses, current settings, and dependency counts, with an explanation for removed contexts still awaiting removal acknowledgement. Enable selects an interface/address, port, and explicitly confirmed source CIDRs. The listener remains enabled with no dependents until explicit disable. Changes are blocked while dependencies or active CONNECT work need it. A lost response requires reloading applied state before another change. Unsupported nodes explain that an upgrade or permission change is needed. Successful application is separate from readiness. See [proxy settings](gateway-proxy.md#managed-listener).
- Secrets, in an online machine's actions menu or detail drawer's More actions menu, opens a right-side panel with names and last-updated timestamps, without creation dates or relative age. Accessible plus, pencil and trash icons add, replace and delete secrets, with confirmation before deletion. Entry and confirmation stay in the side panel. Secret entry uses single-line textarea-backed editors outside a form to avoid Safari's password classification of masked HTML inputs. They have no wrapping or resize handles, disable autocomplete, and mask the value. Editing focuses the value; adding focuses the name. Multiline credentials require the CLI. Values are encrypted to the worker and cleared before sending. The gateway relays ciphertext and audits only machine/operation/outcome. This requires updated nodes, Web Crypto, browser text masking, HTTPS or loopback development, and worker `secrets.manage` permission. Uncertain writes are not retried. See [remote secrets and trust limits](secrets.md#manage-a-worker-from-the-orchestrator).
- Invitations lists metadata and permits revocation. Redeemed invitations link to their machine, which is renamed, disabled, or unregistered from its detail drawer rather than revoked here. Clear history, after confirmation, deletes revoked invitations and unredeemed ones past expiry and hides redeemed ones; the hidden records keep their machines' credentials, so enrolled machines keep working. Revoked incomplete Hybrid invitations disappear immediately, with internal records retained until timeout retirement cleans up an installed half. Pending invitations stay. `control machines invites clear` does the same. Revoking a redeemed invitation also revokes its installation key, disconnecting its gateway session. Accepted work and established direct sessions may continue.
- Access keys creates, renames, and revokes common fleet keys. Renaming changes only the label. New secrets are displayed once. Account keys are not listed on this page. Installation commands also cannot be recovered after their dialog closes.
- Account changes the current browser password. The account menu under the avatar links there, selects the system, light, or dark theme, and signs out after confirmation. Sign out revokes only the current browser session.
- Operator-only Accounts provisions and disables private fleets and sets their browser passwords. Account creation shows the CLI account key once.
- Operator-only Updates displays separate gateway progress, relay-carrier blockers, and per-node reasons such as `waiting-idle`, `waiting-gateway`, and `waiting-proxy`. The gateway switches first; idle nodes then update independently, with at most two live commits. Offline installation participants deferred after the two-minute reconnection grace remain explicitly pending, with admission shown as unknown rather than the last stale reservation. Unresolved commit intents still block another publication until reconciled. A confirmed release check may begin a verified rollout; gateway restarts separately drain relay traffic without cancelling streams. Development bundle publication stays in `control update push DIR`. Machine rows retain Updating with a local progress detail, without exposing global or other-fleet blockers.

A pending invitation name conflict offers an explicit checkbox to retract the existing invitation on the next submission. It never forces or retries a request automatically. A lost mutation response instructs the user to refresh and inspect state before submitting again.

Machine rows on Overview and Machines show a neutral **Proxy** chip when the node advertises configured proxy hosting, including hosting with no dependents. **Via proxy** identifies nodes reporting a configured gateway proxy route. Both remain visible while offline or when proxy checks fail. Tooltips identify the gateway URL when available; Via proxy also names the configured proxy worker when it is in the fleet snapshot, and includes the endpoint. These chips describe configuration, not connectivity or readiness. Machine status, connection counters, and endpoint readiness in the drawer remain separate.

Following an update, a Proxy chip can be visible before a fresh readiness check succeeds. Add machine explains when configured proxies are not ready. While Direct is selected, its proxy choices follow snapshot refreshes without replacing the form or clearing typed values. An explicit proxy selection remains visible if readiness is lost, and is rejected before submission rather than silently becoming Direct. Readiness recovery never submits or retries an invitation. Workers check promptly after gateway reconnection or maintenance resumption, with bounded faster retries for failed checks.

Hybrid rows show each proxy chip once if either context has that configuration, with the tooltip identifying the context. Switching User/System does not hide the host's proxy roles or change action targets. Drawers show only the selected node's own configuration chips. Older nodes without route-reporting metadata omit Via proxy until upgraded; installation dependencies alone do not prove the node's current configuration.

Each Hybrid invitation appears as one row, grouped by its gateway-issued `hybridId` and named from the User invitation. Its Startup column says Hybrid, and Revoke targets the User invitation to revoke the pair. The row remains Pending until both invitations redeem, or shows Revoked if either is revoked. Separate attempts with the same machine name remain separate rows, and unrelated `-system` names are never grouped. Clear history counts displayed invitation rows, not the internal User/System records.

Right-click a machine row on Overview or Machines, or use its three-dot Actions button, to view details, rename, change startup context for a User node, enable/disable, wake when eligible, or unregister. Rename and lifecycle actions keep their existing confirmations, including the typed name for unregister. Shift+F10 or the Context Menu key opens the menu from a focused machine name; arrow keys, Home, and End move between actions, and Escape closes it. Shift+right-click keeps the browser's native context menu. Unregistering one Hybrid context names the other, which stays registered and running unless you also select it in the dialog. Removing both sends two requests; if the second fails, the dialog says which context remains.

The console does not submit tasks, open peer connections, read task logs/results, stream artifacts, or manage host-local tunnels. Account views contain only their fleet. The operator can administer users and gateway-wide updates, but its machine view and machine actions remain scoped to the legacy operator fleet, not all users' machines.

### Change an installed User node's startup context

Choose **Startup context** in the machine's actions menu. In the detail drawer, Startup context and Unregister are under the three-dot More actions button; Rename, Enable/Disable, and Wake when available stay visible. This is available for Linux, macOS, and Windows nodes reporting User execution, including offline nodes. **Apply startup context** first requests the change from the node through the gateway. The node must be idle and permitted by `service.startup` allow rules. No arbitrary scripts, remote profile paths, UAC, or sudo prompts are sent. If the node cannot apply the change, the console displays a command to run locally. The optional configuration path affects that fallback only; the remote request always applies to the running profile.

- Windows System can apply remotely only when the installed node itself already runs with administrator rights. Its verified helper waits for the old supervisor to stop and migrates the original profile to boot-time LocalService startup. A normal limited User node returns a local fallback, `control service start --mode auto`, with `--config` when supplied. Run it in Administrator PowerShell under the same user, not through a node execution provider. It retains identity, workspace, and history, and needs no invitation or published installer. Admission is not completion: the dialog waits for that identity to reconnect and report System execution. If unconfirmed after one minute, inspect the machine and `startup-change.log` before using the displayed recovery command.
- Linux/macOS System needs a separate root-owned profile and an unused routing name. The command first runs `control service uninstall --mode user` against the existing profile, then the new System installer with sudo. The old files and registration remain, but identity, credentials, workspace, and task history are not migrated. Verify the new System node before separately unregistering the old registration. To keep the original name instead, follow the explicit [Unix replacement procedure](installation.md#choose-a-startup-context).
- Hybrid creates a same-name replacement User invitation and an independent `NAME-system` invitation. Run it from the user's shell with sudo available on Unix, or Administrator PowerShell under that user on Windows. It re-enrolls the original User profile and installs a protected companion. Both contexts must report online before the dialog reports completion. An existing companion is not replaced; manage it separately. Names longer than 56 characters need renaming first.

System and Hybrid installation commands expire after 15 minutes and are shown only once. Generating one does not stop, unregister, or elevate the existing node. Pending invitation conflicts require explicit retraction confirmation; lost responses are never automatically retried. See [startup contexts](installation.md#choose-a-startup-context) and [Hybrid isolation](installation.md#hybrid-user-and-system-contexts).

### Hybrid rows and counters

A Hybrid host has one machine row with User and System chips. The gateway supplies the pairing from its enrollment records; similarly named unrelated machines are not grouped. The machine counter, filter counts, and online/offline totals count hosts once, not their System companions. A host is online if either context is online, and offline only if both are offline. Offline context chips are struck through and remain selectable. The row's status reflects connected contexts regardless of chip selection, with updating, busy, and reserved reports taking precedence over idle reports. Updating also remains visible while either context is disconnected within the gateway's restart display grace, even if its companion reports idle. This does not change online counts or action targets. An offline row's last-seen age uses the more recent observation. Active work still counts real operations in both contexts.

An idle row shows `Active … ago` using the latest Control work timestamp reported by its idle contexts. If neither reports one, the detail stays blank. The drawer shows only the selected context's activity.

User is selected by default, including when only System is online. When the selected User context is offline and its System companion is online, the row shows System CPU, memory, disk, and connection/tunnel counts instead. Resource and connection sorting uses those displayed values. User telemetry returns when User reconnects. This display fallback does not change the selected context, drawer, or action targets. An explicitly selected offline System context does not borrow User telemetry; when both are offline, live metrics remain unknown.

Select System to inspect that context's details or manage it; the drawer shows its actual routing name. Rename is host-wide when both contexts are registered, regardless of the selected chip. Its form starts with the User name and explains that System becomes `NEW_NAME-system`. It sends one User rename request; the gateway validates and commits both names atomically, including while offline. A conflict on either alias leaves both unchanged. Other actions, including disable and unregister, still target the selected context. Chip selection stays in memory across polling and is cleared at sign-out. It does not change CLI/MCP routing. User work does not automatically retry as System; explicitly choose System for an authorized operation that requires elevation.

### Custom machine order

Hold a machine's platform icon and drag its row to a new position on Overview or Machines. Rows shift apart to open a full-height, outlined slot labeled "Drop NAME here" with its destination position. The machine lands in that slot when released, and the order saves immediately. There is no ordering dialog or Save button. Dragging near the top or bottom scrolls the list. Escape, a cancelled pointer gesture, or dropping outside the list cancels the move and closes the slot. With the icon focused, Alt+Up and Alt+Down move the machine using the keyboard. Clicking the icon alone does not open machine details.

The order is saved in this browser for the signed-in fleet at this gateway, including across reloads and sign-outs. It does not sync to other browsers or affect CLI/MCP discovery, terminal dashboards, or worker selection. Stable identities preserve positions through renames, and Hybrid User/System contexts share one position regardless of the selected chip. New machines follow saved machines in name order; removed machines are ignored.

Search, state filters and Overview may hide machines. Reordering moves only the visible machines between their existing positions in the full list; hidden machines keep their positions. Column headers temporarily select another sort without erasing the saved order. Dragging starts a custom order from the displayed sort; reloading restores the saved custom order. Polling does not replace rows during a drag. If browser storage is unavailable, dropping reports an error without changing the saved order.

## Refresh and accessibility

When the fleet reports classified discrete GPUs or NPUs, machine tables add a GPU/NPU column. Integrated, virtual/remote display, and unclassified adapters are hidden, including in drawers. The main bar shows loaded dedicated memory, with used/total bytes underneath; any compute utilization is separately labeled. Model names appear only in hover tooltips on each device's usage block, in tables and drawers. Sorting uses the highest known dedicated-memory percentage, with unknown values last. GPU/NPU metrics follow the Hybrid fallback above; they do not change action targets. Unsupported readings stay unknown and offline contexts hide cached usage. Windows DXCore and adapter-wide memory counters supply dedicated-memory capacity/usage for supported AMD, Intel, and NVIDIA devices. See [platform support](dashboard.md#gpu-resources).

In machine drawers, GPU and NPU memory usage appear in the Resources grid alongside CPU, memory, and disk, with matching labels and bar widths.

Machine-row versions are capped at 23 character units and ellipsized instead of widening the table. Hover shows the full version, which also remains in the detail drawer. Narrow layouts hide row versions.

Desktop machine tables use fixed status, connection, and resource column widths, leaving the remaining space for machine names. Status and metric refreshes do not resize the columns. Long status details wrap within their cell. Smaller screens scroll the table horizontally until the stacked mobile layout applies.

A detected device without a dedicated-memory percentage shows `NPU detected` or `GPU detected` instead of a bar. Capacity or used bytes remain visible when known; otherwise the subtitle reads `Memory unavailable`. This distinguishes inventory-only devices such as Surface's Qualcomm Hexagon NPU from machines with no accelerator. Model names remain in tooltips, and offline devices still hide cached usage.

The console reads gateway snapshots every five seconds while its tab is visible. Refresh requests do not initiate resource sampling or peer probes. Gateway metrics retain their original collection times; node health expires under the same rules as the terminal dashboard. Missing fresh health means unknown work, not zero work. Reported work is a count of tracked operations, not necessarily distinct jobs.

Failed requests preserve the last view and show a warning with the last update time. The console supports light/dark themes, narrow layouts, labeled native form controls, keyboard-scrollable tables, keyboard focus, modal dialogs, and reduced motion. Browser local storage contains only theme selection and fleet-scoped machine ordering IDs. Passwords, session tokens, keys, and installation commands are not stored there.

## HTTPS and reverse proxies

Use the existing [Caddy](gateway.md#5-enable-public-https) or [expose](expose.md) deployment with the gateway on loopback and `CONTROL_PUBLIC_URL=https://control.example.com`. Preserve the original HTTP Host header. Password endpoints and console pages reject hosts that differ from the configured public origin.

TLS can terminate directly in Control or at a trusted loopback proxy. The console accepts a configured HTTPS public origin over a plaintext upstream only when the socket peer is loopback. It does not trust `Forwarded` or `X-Forwarded-*` headers. A proxy on another host or container network must use TLS to the gateway, or connect through a trusted local forward. Keep the plaintext gateway listener inaccessible from public networks. Do not put a second login in front of the whole gateway, because CLI and node API traffic must retain bearer authentication.

Without a public URL, direct HTTPS works. Plain HTTP is accepted only for direct loopback development with a loopback Host such as `http://127.0.0.1:7330`. A configured loopback HTTP public URL is also supported. Remote plaintext access is rejected, including password provisioning.

## Credentials, sessions, and limits

SQLite schema version 5 added browser password records referencing immutable existing user IDs. Passwords use Argon2id with a random 16-byte salt, 19 MiB of memory, two passes, one lane, and a 32-byte derived hash. Password work runs outside the gateway mutation lock, with at most two concurrent verifications/derivations and no waiting queue. Changes commit before acknowledgment; failed writes retain the old password and sessions.

Successful login generates a new 256-bit opaque cookie. The gateway persists only its digest and session metadata in SQLite schema version 7, with a bounded in-memory cache. Cookies are HttpOnly, SameSite=Strict, and Secure for HTTPS origins. Sessions expire after 24 hours without authenticated requests or 7 days total. Polling counts as authenticated activity. New login cookies last 7 days; cookies issued by older gateways retain their shorter browser expiry until the next sign-in. Valid sessions survive gateway updates and restarts without resetting creation or last-activity timestamps. Activity is checkpointed at most once per minute and flushed on graceful shutdown; a crash can lose up to one minute of recent activity, expiring an idle session that much earlier. Account disable and password revisions are rechecked on authenticated requests and startup. Operator sessions also require configured superuser administration. Sessions created by older, memory-only gateways still require a fresh login after the first upgrade.

There are at most 4,096 sessions, at most 32 per username, and a bounded login-failure map. Signing in beyond a username's limit ends that username's oldest session. Over a 15-minute window, admission permits up to 10 failed verifications per username, 60 per socket source address, and 120 globally. Successful logins are not counted. A username without recent failures can still sign in after other clients exhaust the source or global budgets; once it fails, it shares them. Failed current-password checks during a password change count as failures. Loopback reverse proxies share a source-address allowance because forwarded addresses are not trusted. An overloaded verifier returns HTTP 429 rather than queueing password work.

Browser mutations require both the exact same Origin and a session-bound CSRF header. Login requires the same Origin too. Responses use `no-store`, a restrictive Content Security Policy, no-referrer policy, and frame blocking. Cookies authorize only an explicit management-route allowlist under `/console/api/`. They do not authenticate `/v1/` APIs, node registration, or peer/client WebSockets. CLI keys never need to be copied into a browser.

Back up the gateway state before upgrading. Earlier gateways reject schema version 7. Restoring an older executable does not reverse the database migration. Browser access has no MFA; protect operator passwords and the gateway state accordingly.

## Activity log

Activity lists sign-ins, failed sign-ins, sign-outs, and management changes newest first: key creation, rename, and revocation; invitation creation and revocation; machine enrollment, rename, enable/disable, and unregistration; account creation, disable, and browser password changes; and, for the operator, update publication, release checks, and [online database backups](gateway.md#online-backup) taken on the gateway host. Each event records its time, fleet, actor (browser login, or account name with the key ID for bearer keys), action, target, a short detail such as a previous name, and source IP. Events never contain passwords, keys, installation commands, or execution arguments. Filter by category and load older pages; new events appear at the top while the page is open.

Account owners see their own fleet's events. The operator sees every fleet, including failed sign-ins for unknown usernames, which belong to the operator fleet. The source IP is the direct TCP peer, because forwarded headers are not trusted; behind a reverse proxy it is the proxy's address.

Schema version 6 adds `audit_events`. Each event commits in the same SQLite transaction as the change it describes, so a change is never acknowledged without its record. Sign-in and sign-out require durable session and audit writes; a failed write returns an error without issuing or clearing the cookie. A failed sign-in still proceeds if its audit write fails. Update publication and release checks live in the update store, so their events are written immediately afterwards and a failed write is logged. The gateway keeps the newest 10,000 events per fleet and 100,000 overall, so one fleet's activity cannot displace another fleet's history. Failed sign-ins are limited separately to the newest 2,000 so password guessing cannot displace management history. Retention runs after every 256 written events rather than on each commit, so a budget can briefly hold up to 256 more events. Clearing with a cutoff compares instants, including fractional seconds. `GET /v1/audit` and `control audit list [N]` read the same log.

Clear log removes all events, or only those older than 7 or 30 days, after confirmation. Account owners clear their own fleet; the operator clears every fleet. Each fleet that loses events receives one "Cleared activity log" event with the actor, source IP, and count, written in the same transaction, so history cannot disappear without a trace. `DELETE /v1/audit` and `control audit clear [DAYS]` do the same.

## Verification

Asynchronous form completions are scoped to their original session and form. Key, account and installation-command issuance block ordinary dialog dismissal while pending, so a one-time response is not silently discarded by Cancel. Session expiry still clears the dialog; responses from the previous session cannot display credentials or mutate a replacement form. A lost mutation response remains uncertain, never confirmed success or permission to replay.

Activity refreshes and older-page requests share a query generation. Navigation, filter changes and session changes invalidate older responses. If more new events arrive than fit in the latest page, the console resets to that continuous page and its pagination cursor instead of retaining an unreachable gap.

All shipped browser JavaScript uses JSDoc declarations and strict TypeScript `checkJs`. The local check includes every JavaScript file under `internal/gateway/consoleweb/`. Types cover API payloads, state, DOM controls/events, rendering, geometry, and encryption. Optional readings remain distinct from zero. The JSON API implementation returns `unknown` internally; typed route overloads describe the gateway's responses to callers. Required DOM lookups fail with the selector in their error; optional lookups use `find()`.

Run the mandatory frontend type checks with Node.js 22+:

```sh
npm --prefix tests/console ci
make typecheck-console
```

TypeScript 7.0.2 runs the local frontend type check, without coverage tooling or a frontend typing CI job. It is a development-only dependency and emits no JavaScript. The Go bundle builder separately strips comments for embedding; deployment still needs only the Go binary. See the [frontend typing rules](../AGENTS.md#frontend-typing) before editing browser code. Browser fixtures and icon-generation utilities in `tests/console/` are test tooling, not shipped frontend code.

Core Go tests cover password provisioning, transactional rollback, migration/restart persistence, login, logout, expiry, account disable, password resets, CSRF/origins, secure cookies, verifier limits, fleet isolation, and browser-to-bearer authority separation. They run in the normal native and Compose suites.

Optional browser smoke verification requires Node.js 22+ and an isolated Chromium instance:

```sh
make build
npm --prefix tests/console ci
npm --prefix tests/console exec -- playwright install chromium
npm --prefix tests/console test
```

The smoke script starts its own temporary gateway and node. It does not read saved Control credentials or touch a real fleet. `CONTROL_CONSOLE_TEST_CHROME` can select an installed Chrome executable for headless testing. `CONTROL_CONSOLE_SCREENSHOTS` selects an output directory for desktop/mobile screenshots. Temporary fixture state is retained for inspection; owned processes are stopped when the script finishes.

The favicon and console brand icon use the selected ivory `ctrl` keycap artwork, not the mascot illustration. The original download is preserved in `assets/icon-source.png` from [the selected image](https://chatgpt.com/s/m_6ade4fe3bd8c81918065326918846c74). The generator removes stray pixels with alpha at most 1, crops to the remaining content, and centers it on a transparent square with 1% padding. It writes `assets/icon-cropped.png`, a 512px `assets/icon.png`, a 64px console brand icon, a 16/32/48px ICO, a 32px PNG favicon, and a 180px Apple touch icon. Regenerate them with `npm --prefix tests/console run icons` after installing the browser-test dependencies above. The generator supports `CONTROL_CONSOLE_TEST_CHROME` too. Browser tests check the served assets, dimensions, tight crop, transparency, and matching header/login icons.
